# 河流水质站日 CSV 发布服务

面向科研核验的不可改原件/差分发布 API：原件原字节与差分文档存共享卷，SQLite 只存
目录与摘要，以 SHA-256 固定深度 Merkle 树出具检查点、单件纳入证明与检查点追加证明，
并提供完全离线的验证函数/CLI。两个实例挂载同一卷并发发布，不分叉、不覆盖。

实验室复测常只改站日 CSV 的几行：本服务支持**差分发布**——只提交基稿序号与 1~8 个
字节区间替换，共享卷只存差分与基稿引用、不另存重建全文；差分稿可再作基稿（最多四层），
叶子仍按重建全文的摘要与长度登记，原有 Merkle/离线核验流程零改动。

## 1. 目录结构

```
app/
  config.py       运行配置（DATA_DIR、1 MiB、128 件、树深度 7、差分四层/八段）
  storage.py      原件 blobs/ 与差分文档 deltas/：内容寻址 + 临时文件 fsync + 原子改名
  delta.py        差分纯逻辑：段校验（非空/不重叠/Base64）、区间应用、规范化文档
  reconstruct.py  差分链还原：逐层重建 + 逐跳摘要核验，失败拒绝取件
  db.py           SQLite 持久层：WAL、BEGIN IMMEDIATE 串行化、启动自检、旧库自动迁移
  merkle.py       Merkle 树纯函数：根、纳入证明、追加证明、离线验证
  verify.py       离线核验函数与 CLI（python -m app.verify ...）
  schemas.py      HTTP 响应模型
  main.py         FastAPI 路由（阻塞调用均走线程池）
tests/            41 项 pytest 用例（算法、整件 API、差分 API、故障路径、并发）
scripts/
  demo.sh                 HTTP 端到端演示（含差分提交与重建取件）
  dual_instance_check.py  双进程共卷并发/故障转移/差分链集成检查
Dockerfile
docker-compose.yml        两个实例共卷，端口 8001/8002
```

## 2. 启动

### Docker Compose（交付目标形态）

```bash
docker compose up --build
# 实例 A：http://localhost:8001/docs
# 实例 B：http://localhost:8002/docs
```

两实例镜像相同、挂载同一命名卷 `shared-data`（`/data`），
`MAX_FILE_BYTES=1048576`、`MAX_RELEASES=128`（Merkle 深度 7，128 个叶子槽）、
`MAX_DELTA_DEPTH=4`（还原最多四层差分）、`MAX_DELTA_SEGMENTS=8`（单次 1~8 段）。

卷内布局：`blobs/` 原件、`deltas/` 差分文档、`release.db` 目录库、`tmp/` 临时文件。

### 本地直接运行

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
DATA_DIR=./data uvicorn app.main:app --port 8000
# 打开 http://localhost:8000/docs
```

## 3. API 一览（/docs 可交互演示）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/releases` | 整件表单发布 `station_id`、`sample_date`、`order_no`、`file`；同单同输入重试复用（`reused=true`），异输入 409，超 1 MiB 返回 413，超 128 件返回 409，写盘失败 507 |
| POST | `/releases/delta` | **差分发布**：表单 `station_id`、`sample_date`、`order_no`(新单号)、`base_release_id`(基稿发布序号)、`segments`(JSON 字符串，1~8 段 `{start,end,b64}`) |
| GET | `/releases` | 全部发布目录记录（不含字节，含 kind/base_id/chain_depth） |
| GET | `/releases/{station}/{date}/{order}` | 单条目录记录 |
| GET | `/releases/{station}/{date}/{order}/download` | 取件：整件直读原件；差分件沿链重建原字节，重建失败返回 503 拒绝取件 |
| GET | `/releases/{station}/{date}/{order}/inclusion-proof` | 单件纳入证明（恒 7 步路径；差分件按重建全文登记） |
| GET | `/checkpoints` | 全部检查点（含 0 号空树检查点） |
| GET | `/checkpoints/latest` | 最新检查点（条数 + Merkle 根） |
| GET | `/checkpoints/{seq}` | 任意旧检查点 |
| GET | `/checkpoints/{old_seq}/append-proof` | 旧检查点 → 最新检查点的追加证明 |
| GET | `/health` | 启动自检结果（缺件/差分链重建失败时 `degraded`，拒发证明与下载） |

### 差分请求示例

```json
segments = [
  {"start": 42, "end": 45, "b64": "Ny42"},   // 替换基稿 [42,45) 三个字节为 "7.6"
  {"start": 46, "end": 49, "b64": "OC4z"}    // 两段互不重叠，左闭右开，区间非空
]
```

* `start/end` 为基稿字节偏移，必须 `0 <= start < end <= 基稿长度`，段间互不重叠
  （端点相接允许）；`b64` 为标准 Base64，解码后允许为空串（即删除该区间）；
* 替换可等长可变长；重建全文为空拒绝（422），超过 1 MiB 拒绝（413）；
* 基稿必须与差分稿**同站同日**，否则 422；基稿序号不存在返回 404。

## 4. 差分模型与不变量

1. **只存差分，不存全文**：落盘的是规范化 JSON 差分文档（版本号、基稿 release id、
   基稿重建摘要与长度、全部替换段），按文档自身 SHA-256 内容寻址存入 `deltas/`；
   卷上绝不出现以重建全文摘要命名的副本。
2. **叶子登记重建全文**：`releases.blob_sha256/size` 对整件即原件、对差分件即重建
   全文，因此 Merkle 叶子载荷、纳入证明、追加证明与离线 CLI 完全复用，无需新证明类型。
3. **四层上限**：整件 `chain_depth=0`，每叠一层差分 +1；提交后将达 5 层的请求在落盘
   前直接返回 409 并提示“请改用 POST /releases 整件上传”，不产生记录、不推进检查点。
4. **改回旧字节也并存**：若差分重建结果与某份旧稿逐字节相同，两者是两条独立发布
   记录（单号不同），共享同一份内容寻址原件/各自差分链，**两份稿都能按原字节取回**。
5. **同单重试规则沿用**：同 (站,日,单号) 同重建摘要/长度 → 复用（`reused=true`）；
   同单异内容 → 409，记录不可改。
6. **先核验后落盘、失败不留痕**：先还原并逐跳核验基稿，再原子写差分文档，最后才开
   数据库事务。基稿无法核验（409）或差分落盘失败（507）时，不新增发布记录、不推进
   检查点；孤立差分文档内容寻址、无害且可原样重试。
7. **重建失败拒绝取件**：取件沿基稿链自底向上逐层应用替换段，每跳核验
   ① 文档登记基稿摘要 == 库内基稿记录；② 实际基稿字节 SHA-256 == 登记摘要；
   ③ 本层重建结果 == 该记录登记摘要与长度。任一不符（缺件、文档损坏、卷上篡改）
   返回 503，绝不输出无法核验的字节。
8. **启动自检覆盖差分链**：结构自检（序号稠密、原件/差分文档齐全且摘要相符、基稿
   引用不悬空、链深 1..4、检查点连续）之外，再对每条记录跑一次全链重建；任一链断裂
   即 `degraded`，拒绝发布、证明与取件。

## 5. 核验模型（科研组离线使用）

### 叶子与树

* 叶子载荷为带版本号的规范化 JSON（键排序、无空白）：
  `{v, station_id, sample_date, order_no, blob_sha256, size}`，
  叶子哈希 = `SHA256(0x00 || 载荷)`；内部节点 = `SHA256(0x01 || left || right)`，域分隔防二阶碰撞。
* 固定深度 7 的完整二叉树，未用槽位以公开常量 `EMPTY_LEAF` 占位：
  追加只改变新叶子到根的路径，旧证明不会因树“长高”失效。
* **纳入证明**：7 个兄弟哈希（O(log n)），每步带 `bit` 与下标逐位绑定，防重放到其他下标。
* **追加证明**：把旧前缀与新增区间分别平铺为对齐的完美子树，条目数 ≤ 2×深度（128 件规模最多 8 条）。

### 离线核验（无需服务端、无需网络）

```bash
# 单件：凭留存的纳入证明 + 待验字节（整件为原件，差分件为重建全文），核验站日归属与检查点纳入
python -m app.verify inclusion --proof inclusion.json --file 待验字节.csv

# 历史前缀：凭两个留存检查点 + 追加证明，核验仅追加关系
python -m app.verify append --proof append.json \
  --old-checkpoint cp-old.json --new-checkpoint cp-new.json
```

也可直接导入纯函数：`app.verify.verify_release_bytes`、`app.verify.verify_append_proof`。
篡改字节、替换历史条目、伪造检查点根、证明重放到其他下标均会被拒绝（退出码 1）。

## 6. 崩溃安全与并发不变量

1. **先落盘后入库**：原件/差分文档写临时文件 → `fsync` → `os.replace` 原子改名 →
   `fsync` 目录，成功后才开数据库事务；写盘失败无库记录、临时文件清理、可原样重试。
   临时文件名带 uuid，同进程多线程并发写同一摘要也不会互踩。
2. **串行化发布**：每个发布事务 `BEGIN IMMEDIATE`，双实例写操作被 SQLite 锁串行化，
   后到者等待后重检唯一键 `(station_id, sample_date, order_no)`；无 UPDATE/DELETE 路径。
3. **只增不改**：同键同字节复用、同键异字节 409；检查点与记录均只追加。
4. **启动自检**：重算全部叶子与根，逐件校验卷上原件与差分文档摘要、检查序号稠密、
   检查点连续，并逐条全链重建差分稿；发现缺件/断链即 `degraded`，拒绝发布/证明/下载。
5. **重启有效**：历史检查点根由固定深度树确定，重启后逐点复算一致；差分链引用全部
   在共享卷与库内，重启后已发布差分稿仍按原字节取回，留存证明持续有效。
6. **旧库平滑迁移**：v1 表结构（无 kind/base_id 等列）启动时自动 `ALTER TABLE` 补列，
   历史记录全部视为整件（kind=full, chain_depth=0），迁移后即可继续发差分。
7. 阻塞式磁盘/DB 调用均在任意线程池执行，锁等待不阻塞事件循环；
   写锁冲突在 `busy_timeout` 之外另有 3 次有限重试。

## 7. 测试结果（本环境实测）

* `pytest tests/`：**41 项全部通过**（连续多轮稳定）
  - Merkle 纯函数：根稳定性、纳入/追加证明、篡改/重放/重叠/缺口拒绝、平铺覆盖；
  - 整件 API：发布、幂等复用、409、413/422、128 上限、下载、两类证明与离线核验；
  - 差分纯逻辑：段解析（非空/不重叠/Base64/bool 拒绝）、变长/删除/多段应用、
    规范化文档稳定性、损坏文档拒绝；
  - 差分 API：重建取件、同单重试/冲突、四层链与第五层 409 提示整件上传、
    改回旧字节两稿并存且不复制全文、区间/跨站日/9 段校验、重建大小沿用 1 MiB 规则、
    基稿不可核验不留记录、差分落盘失败不推进检查点、文档篡改 503 拒取、
    纳入证明离线核验、重启全链重建扫描、**并发同单一写一复用**；
  - 故障：写盘失败不留记录、缺件自检与 503 拒服、孤立临时/原件无害、已引用文件被改可检出。
* `scripts/dual_instance_check.py`（两个独立 uvicorn 进程共卷）：**全部通过，0 失败**，
  覆盖整件并发同单/异单、跨实例取件/检查点/证明，并新增差分场景：跨实例四层差分链
  （A/B 交替提交）、每层同单重试复用、跨实例重建字节一致、第五层 409 且检查点不推进、
  改回旧字节两稿并存、`deltas/` 落盘而 `blobs/` 无重建全文副本、第三进程挂同卷的
  故障转移视角下差分稿仍按原字节取回且离线核验通过、重启后可继续追加。
* `scripts/demo.sh`（对真实 uvicorn 实例）：11 步全通过，含差分两段替换、重建取件
  与基稿并存比对、重叠区间 422、差分稿纳入证明与追加证明离线核验、篡改拒绝。
* 旧库迁移专项：以 v1 表结构手工造合法库（含原件与检查点），新代码启动自动补列、
  自检通过、可在历史整件上发差分并重建，再次实例化（模拟重启）后状态一致。
* 手工冒烟：`/docs` 与 `/openapi.json` 均含 `POST /releases/delta`；
  证明规模：纳入证明恒 7 步；追加证明最大条目随条数对数增长（≤ 8）。

## 8. 剩余工作与已知限制（据实说明）

1. **本环境无 Docker 守护进程**，`docker compose` 未实际起容器验证；已用双 uvicorn
   进程共享同一 `DATA_DIR` 做等价并发/故障转移/差分链测试。Dockerfile 与 compose
   配置已交付（YAML 已校验），需在具备 Docker 的环境执行一次 `docker compose up --build` 复核。
2. 沙箱以 seccomp 禁止 `kill` 系统调用，集成脚本无法终止演示进程，改为随机端口 +
   每次独立临时目录；脚本中的“重启”以第三进程挂同卷模拟（故障转移语义等价）。
3. 128 件上限在实现上是固定深度树的叶子槽位数（2 的幂，可经 `MAX_RELEASES` 调整）；
   非 2 的幂配置会在启动时直接报错。四层差分/八段上限可经 `MAX_DELTA_DEPTH`、
   `MAX_DELTA_SEGMENTS` 调整；差分文档解析时的段数自检固定按 8 段上限。
4. 未引入鉴权/传输加密/TLS，定位为内网或网关后的发布服务；对外暴露需前置网关。
5. 共享卷自身的备份与异地容灾未包含在本服务内（卷快照/备份应由基础设施层提供）；
   服务能检出卷上缺件、篡改与差分链断裂，但不会自动恢复字节。
6. 原件类型未强制 CSV 内容嗅探，仅做大小与空文件校验，避免对业务 CSV 方言做过强假设；
   差分按字节区间操作，同样不解析 CSV 语义，调用方需自行保证区间对应预期行/列。
7. 差分提交的 `segments` 以表单 JSON 字符串承载（multipart 不支持嵌套 JSON 字段），
   单请求总体大小仍受重建全文 1 MiB 上限约束，未对请求体另设独立限额。
